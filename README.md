# Stargazers

A simple [Obelisk](https://github.com/obeli-sk/obelisk) webhook endpoint and a workflow
that monitors GitHub repositories. Every step is persisted and replayed during crash recovery.

## Workflow Code Example - `star-added`

```js
export default function star_added(login, repo) {
    // 1. Persist the user giving a star to the project.
    const description = addStarGetDescription(login, repo);
    if (description != null) return;
    // 2. Fetch the account info from GitHub.
    const info = accountInfo(login);
    // 3. Fetch the prompt from the database, picking a model if none is set.
    const settingsJson = withModel(getSettingsJson());
    // 4. Generate the user's description.
    const generated = llmRespond(info, settingsJson);
    // 5. Persist the generated description.
    updateUserDescription(login, generated);
}
```

Here is the complete [workflow source](./src/workflow/star-added.js); its signature is declared in
[deployment.toml](./deployment.toml).

## Layout

All components are plain JavaScript, loaded by Obelisk without a build step:

| Directory | Component |
|-----------|-----------|
| [webhook](./src/webhook/) | GitHub webhook endpoint, starts the workflows |
| [ui](./src/ui/) | Page listing the latest stargazers, on the private `internal` server |
| [workflow](./src/workflow/) | Workflows orchestrating the activities |
| [activity/github](./src/activity/github/) | Account info and stargazers from the GitHub GraphQL API |
| [activity/llm](./src/activity/llm/) | Description generated by an LLM over the Chat Completions API |
| [activity/db](./src/activity/db/) | Persistence in [Turso](https://turso.tech) (libSQL), migrations applied by `just migrate` |

[app.toml](./app.toml) holds the secrets and outbound HTTP policy, [deployment.toml](./deployment.toml)
the components and their signatures. The same app is also implemented in Rust, see [rust](./rust/).

## Deploying to Obelisk Cloud

Requires [Obelisk](https://github.com/obeli-sk/obelisk), [just](https://github.com/casey/just) and
[Node.js](https://nodejs.org) for the migration. With [Nix](https://nixos.org/) and
[direnv](https://github.com/direnv/direnv), `cp .envrc-cloud-example .envrc` provides all of them
and keeps the variables below.

### 1. Clone and log in
```sh
git clone https://github.com/obeli-sk/demo-stargazers.git
cd demo-stargazers
obelisk generate app-name   # picks a unique name and writes it to app.toml
```

### 2. Set up Turso and the webhook secret
Create a [Turso](https://turso.tech) database and a token, then pick a secret for the GitHub webhook:
```sh
turso db create stargazers
export TURSO_LOCATION="https://$(turso db show stargazers --url | sed 's#^libsql://##')"
export TURSO_TOKEN="$(turso db tokens create stargazers)"
export GITHUB_WEBHOOK_SECRET="$(openssl rand -hex 20)"
just migrate
```
`just migrate` creates the schema and stores a basic prompt for the LLM, see
[LLM settings](./src/activity/db/README.md#llm-settings).

### 3. Push
```sh
obelisk cloud app push --env TURSO_LOCATION --secret TURSO_TOKEN --secret GITHUB_WEBHOOK_SECRET
```
LLM and GitHub requests go through the cloud integrations (`[cloud.integrations]` in `app.toml`),
so no API keys are needed. The LLM activity speaks only the OpenAI Chat Completions API
(`/v1/chat/completions`). Unless the LLM settings name a model, the workflow uses the first
one offered by the LLM integration.

### 4. Set up the GitHub webhook
`obelisk cloud app status` prints the app's URL, `https://<app>.obelisk.works/`.
Create a webhook that sends Star events signed with `GITHUB_WEBHOOK_SECRET` and save its ID for cleanup.

```sh
EXTERNAL_ENDPOINT=$(obelisk cloud app status --json | jq --raw-output .app.endpoints.external) # "https://<app>.obelisk.works"
OWNER=...
REPO=...
HOOK_ID=$(gh api "repos/$OWNER/$REPO/hooks" \
  -f name=web \
  -f 'events[]=star' \
  -f "config[url]=$EXTERNAL_ENDPOINT" \
  -f 'config[content_type]=json' \
  -f "config[secret]=$GITHUB_WEBHOOK_SECRET" \
  --jq '.id') && printf 'Created webhook %s\n' "$HOOK_ID"
```
GitHub pings the new webhook; the delivery appears under the repository's Settings, Webhooks.
Alternatively, in the repository go to Settings, Webhooks, Add webhook:
* Payload URL: the app's URL
* Content type: `application/json`
* Secret: the value of `GITHUB_WEBHOOK_SECRET`
* Events: select individual events, only Stars

### 5. Add a star and check the database
Star the repository. The webhook starts the `star-added` workflow, which stores the stargazer and
generates their description. Open `https://internal--<app>.obelisk.works/<owner>/<repo>` in a browser
to see the latest stargazers of the repository, or `/` for all of them. The internal host is private:
the browser signs in through the cloud. Or query the database directly:
```sh
turso db shell stargazers "SELECT * FROM users"
```

### 6. Delete the test webhook

After testing, use the `HOOK_ID` from step 4. [GitHub webhook deletion documentation](https://docs.github.com/en/rest/repos/webhooks#delete-a-repository-webhook)

```sh
gh api --method DELETE "repos/$OWNER/$REPO/hooks/${HOOK_ID:?Set the test webhook ID}"
```

If you created the webhook in the GitHub UI or lost its ID, list the webhooks for the same
`OWNER` and `REPO`. Set `HOOK_ID` to the ID whose URL matches your test endpoint, then run
the delete command.

```sh
gh api --paginate "repos/$OWNER/$REPO/hooks" --jq '.[] | {id, url: .config.url, events}'
```

## Running locally

### Environment
With Nix and direnv, `cp .envrc-local-example .envrc`, fill in the values and `direnv allow`.
Otherwise install the tools listed in the [Nix flake](./flake.nix); optionally
[Cloudflared](https://github.com/cloudflare/cloudflared) for exposing the webhook endpoint.
The exact versions used for development and testing are in [dev-deps.txt](./dev-deps.txt).

Besides the Turso variables and the webhook secret from the cloud setup, local runs need the
keys that the cloud integrations otherwise provide:
```sh
export GITHUB_TOKEN_STARGAZERS="..."  # see the GitHub activity README
export LLM_API_KEY="..."              # OpenAI API key
```
Optionally set `LLM_BASE_URL` (default `https://api.openai.com`) to use another endpoint implementing
the Chat Completions API, and `GITHUB_API_BASE_URL` (default `https://api.github.com`). Both base URLs may include
a path; the outbound HTTP rules allow only `<base>/v1/chat/completions`, `<base>/v1/models` and `<base>/graphql`.

Each component directory describes its prerequisites: [Turso](./src/activity/db/README.md),
[GitHub](./src/activity/github/README.md), [LLM](./src/activity/llm/README.md), [webhook](./src/webhook/README.md).

### Running
```sh
obelisk generate app-name   # once, Obelisk refuses the placeholder name
just migrate
just serve
```

Wait for the following lines in the process output:

```log
HTTP server `webui` is listening on http://127.0.0.1:8080
HTTP server `external` is listening on http://127.0.0.1:9090
HTTP server `internal` is listening on http://127.0.0.1:9091
API startup token: ...
Serving API requests at 127.0.0.1:5005
Obelisk <version> is ready
```

`--dev` prints the API startup token; clients such as the CLI send it via `OBELISK_API_TOKEN`.
The workflow can be started using the Web UI.
The webhook endpoint can be triggered using `curl` or by setting up the webhook
in a GitHub repo. See the [webhook README](./src/webhook/README.md) for details
on how to set up GitHub and a https tunnel to the local instance.

### Testing
```sh
just test-unit   # migration runner tests
just test-e2e    # webhook to database, against real GitHub, local sqld and a mocked LLM
```

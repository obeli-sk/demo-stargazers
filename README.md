# Stargazers

A simple [Obelisk](https://github.com/obeli-sk/obelisk) webhook endpoint and a workflow
that monitors GitHub repositories. Every step is persisted and replayed during crash recovery.

## Workflow Code Example - `star-added`

```js
export default function star_added(login, repo) {
    // 1. Persist the user giving a star to the project.
    const description = addStarGetDescription(login, repo);
    if (description != null) return;
    // 2. Fetch the account info from GitHub.
    const info = accountInfo(login);
    // 3. Fetch the prompt from the database.
    const settingsJson = getSettingsJson();
    // 4. Generate the user's description.
    const generated = llmRespond(info, settingsJson);
    // 5. Persist the generated description.
    updateUserDescription(login, generated);
}
```

Here is the complete [workflow source](./workflow/star-added.js) and the
[WIT file](./workflow/wit-interface/stargazers_workflow/workflow.wit) describing the interface.

## Layout

All components are plain JavaScript, loaded by Obelisk without a build step:

| Directory | Component |
|-----------|-----------|
| [webhook](./webhook/) | GitHub webhook endpoint, starts the workflows |
| [workflow](./workflow/) | Workflows orchestrating the activities |
| [activity/github](./activity/github/) | Account info and stargazers from the GitHub GraphQL API |
| [activity/llm](./activity/llm/) | Description generated by an OpenAI-compatible LLM |
| [activity/db](./activity/db/) | Persistence in [Turso](https://turso.tech) (libSQL), schema migrations |

[app.toml](./app.toml) holds the secrets and outbound HTTP policy, [deployment.toml](./deployment.toml)
the components. The same app is also implemented in Rust, see [rust](./rust/).

## Deploying to Obelisk Cloud

Create a [Turso](https://turso.tech) database (see the [db activity README](./activity/db/README.md)), then:

```sh
git clone https://github.com/obeli-sk/demo-stargazers.git
cd demo-stargazers
obelisk cloud auth login
obelisk generate app-name   # picks a unique name and writes it to app.toml
obelisk cloud app push -a app.toml -d deployment.toml --fill
```

`--fill` prompts for `TURSO_TOKEN`, `TURSO_LOCATION` and `GITHUB_WEBHOOK_SECRET`.
LLM and GitHub requests go through the cloud integrations (`[cloud.integrations]` in `app.toml`),
so `LLM_API_KEY` and `GITHUB_TOKEN_STARGAZERS` are not needed. The LLM settings stored in the
database must name a model offered by the LLM integration, see [Inserting the LLM settings](./activity/db/README.md#inserting-the-llm-settings).

The webhook is served at `https://<app>.obelisk.works/`; `obelisk cloud app status` prints the
endpoints. Point a GitHub repository webhook at it (only "Stars" events, the same
secret as `GITHUB_WEBHOOK_SECRET`), as described in the [webhook README](./webhook/README.md).

## Running locally

### Environment
If [direnv](https://github.com/direnv/direnv) and [Nix](https://nixos.org/) are available:
```sh
cp .envrc-example .envrc
direnv allow
```
Otherwise install [Obelisk](https://github.com/obeli-sk/obelisk) and
[just](https://github.com/casey/just); optionally [Cloudflared](https://github.com/cloudflare/cloudflared)
for exposing the webhook endpoint. The exact versions used for development and testing are in [dev-deps.txt](./dev-deps.txt).

The activities read the following environment variables:
```sh
export LLM_API_KEY="..."              # OpenAI API key
export GITHUB_TOKEN_STARGAZERS="..."  # see the GitHub activity README
export TURSO_TOKEN="..."
export TURSO_LOCATION="https://[yourdb].turso.io"
export GITHUB_WEBHOOK_SECRET="some-secret"
```
`TURSO_LOCATION` is the database base URL including the scheme.
Optionally set `LLM_BASE_URL` (default `https://api.openai.com`) to use another OpenAI-compatible
endpoint, and `GITHUB_API_BASE_URL` (default `https://api.github.com`). Both base URLs may include
a path; the outbound HTTP rules allow only `<base>/v1/chat/completions` and `<base>/graphql`.

Each component directory describes its prerequisites: [Turso](./activity/db/README.md),
[GitHub](./activity/github/README.md), [LLM](./activity/llm/README.md), [webhook](./webhook/README.md).

### Running
```sh
just serve
```

Wait for the following lines in the process output:

```log
HTTP server `webui` is listening on http://127.0.0.1:8080
HTTP server `external` is listening on http://127.0.0.1:9090
HTTP server `internal` is listening on http://127.0.0.1:9091
API startup token: ...
Serving API requests at 127.0.0.1:5005
Obelisk <version> is ready
```

`--dev` prints the API startup token; clients such as the CLI send it via `OBELISK_API_TOKEN`.
The workflow can be started using the Web UI.
The webhook endpoint can be triggered using `curl` or by setting up the webhook
in a GitHub repo. See the [webhook README](./webhook/README.md) for details
on how to set up GitHub and a https tunnel to the local instance.

### Testing
```sh
just test-unit   # migration and statement splitting tests
just test-e2e    # webhook to database, against real GitHub, local sqld and a mocked LLM
```
